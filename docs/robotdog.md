# Robotdog Q-04 — Spot-inspired quadruped, shared PPO policy

`robotdog.html` is independent of the existing 2D robot, evolution lab, swing, calendar, mindmap and blogs. No navigation/database rows or other experiments' storage are changed.

## Mechanism and visual reference

References inspected for this update:

- Current manufacturer mass specification and front sensor reference: https://bostondynamics.com/products/spot/ and https://bostondynamics.com/wp-content/uploads/2023/06/spot-section.png
- Official Spot anatomy, hip axes and knee flexion: https://dev.bostondynamics.com/docs/concepts/about_spot.html
- Its front/side drawings: https://dev.bostondynamics.com/_images/frontview.png and https://dev.bostondynamics.com/_images/sideview.png
- Public ROS model at a pinned revision: https://github.com/rai-opensource/spot_description/blob/156d1802bfb117f219dbfce7597d283d5fabc968/spot_description/urdf/spot_macro.xacro

The public model supplies reference joint spacing, axes and link lengths; no manufacturer mesh, texture or logo is bundled. Our procedural yellow/black shell is an approximation. The front is a shallow central grille with two vertical groups of flush sensor panels. The back-mounted arm, its controls, its rendering and its 8 kg mass contribution are removed. `robotdog-arm.mjs` is not imported by the new app; keeping that legacy file avoids breaking a previously cached page.

Each leg is a real Three.js parent/child chain: body → X abduction → lateral carrier → Z hip pitch → upper link → Z knee flexion → one solid lower link → rubber foot. The lower link deliberately has no double/open rail. The same sequence calculates the physical foot positions and analytic contact Jacobian. Mesh orientation is no longer inferred with a shortest-arc quaternion from two endpoints, which discarded the hinge roll and could flip/twist the covers.

Coordinates are SI units, +X forward, +Y up, +Z left (converted from the reference model's Z-up convention). Chassis shell: 0.88 × 0.22 × 0.22 m. Hip roots: X ±0.29785 m, Z ±0.055 m; lateral carrier 0.110945 m. Upper/lower link: 0.3205/0.330 m; foot radius 0.034 m. Total simulated mass is 33.8 kg (current official Spot specification including battery); gravity 9.81 m/s². Motor caps are 45/45/115 N·m, following the public model's settings, not a claim of certified hardware ratings. Knees flex only 0.245..2.79 rad. Pitch limits are -1.4..1.25 rad; conservative inward/outward abduction limits are mirrored by side to reduce legs crossing the body. These simulator limits intentionally differ from the robot's full hardware envelope.

## Physics and its limits

This is a lightweight reduced articulated dynamics model, not a calibrated hardware-transfer simulator. Body angular velocity and 12 joint velocities use a coupled 15×15 mass matrix, with separate whole-system COM translation. Estimated segment masses sum to the official 33.8 kg: chassis 24 kg; each hip 0.9 kg, upper leg 1.3 kg, lower leg 0.2 kg and foot 0.05 kg. These segment values are estimates, not manufacturer measurements. Joint PD torques are internal forces: moving legs in free flight cannot lift the overall COM against gravity.

Sequential normal/friction impulses enforce distributed hull/leg/foot contact. Joint limits also use impulses. Small mass-weighted position corrections distribute residual contact error across body and joints; the old whole-body lift/downward-velocity clamp is removed. Render interpolation uses quaternion slerp and at most 2 mm visual clearance correction. Collision uses sampled shapes and smoothed height fields, so it is an approximation; small residual penetration is measured in tests rather than claimed absent.

There are no stored walk/get-up animations or injected forward propulsion. Actions control 12 bounded PD target positions. Physics runs at 120 Hz; policy decisions and PPO environment steps run at 30 Hz in both training and live execution. Training is in a module Worker. Observation/render loops and learning are separate. Training observation replays actual recorded simulation traces; live Model Run continuously evaluates the saved policy in physics.

Terrain height and normals are shared by sensors, contact and procedural scenery. Seven choices have distinct palettes and features: meadow with scattered long grass and small physical stones; rolling grassy hills; dense rocky gravel; dirt trails ascending/descending grassy slopes; grey rounded stone steps; a grassy ridge. Deterministic rock domes have matching contact height and rendered geometry. A local patch follows movement without resetting camera orbit/zoom. Grass/rocks are instanced; textures are procedural and no external image is downloaded at runtime. No shadow maps or postprocessing. Initial scene measured about 37,874 triangles and 55 draw calls. Rendering targets 60 fps when active, with device-dependent pixel-ratio limits; actual frame rate depends on the device.

## Real PPO, one robot

`robotdog-ppo.mjs` implements its own multi-output Actor/Critic, stochastic tanh-Gaussian sampling, joint log probabilities, GAE, PPO clipped objective, Value Loss, transformed entropy gradients, gradient clipping and Adam. Exact network gradients are checked against finite differences. This code does not import another experiment's physics, reward, learner or conceptual task controllers.

The actor has 68 observations, 24 tanh hidden units and 12 continuous actions; the critic uses the same input dimensions with one value output. Observations: local height, projected up direction, local linear/angular velocity, 12 angles, 12 angular velocities, four actual contact flags, previous 12 actions, three command values, six goal bits and nine current terrain-height probes. No evaluation outcome or future simulator state is an observation.

The six goals are balance, forward walking, backward walking, turning, get-up and push resistance. These use **one shared actor weight array**, not six separately loaded models. Selecting a goal changes the command/observation. “여러 목표 함께 학습” cycles goals evenly between episodes. Target speed accepts 0.1–10 m/s as a command range, not a guaranteed achievable speed.

Rewards combine local height × uprightness, command tracking, actual signed progress, recovery-potential change, stability and small effort/action-change costs. Walking has a standing-still cost. A success flag requires the corresponding real goal: distance for walking, yaw change for turning, sustained upright recovery for get-up, and stable standing for balance/push. A positive reward alone is not success. Get-up begins side-lying and does not end immediately for being down. Time limits are truncations and bootstrap value; true failure termination does not bootstrap. Training does not stop merely because a task succeeds.

PPO updates after ≥256 collected control transitions, normally with four epochs and 64-sample minibatches, with KL early stopping. Partial final rollouts ≥32 samples may also update. The current actor keeps learning; the integrated execution policy is adopted only after a higher average reward on two fixed seeds per relevant goal with bounded per-goal score regression. This lightweight screening is not comprehensive validation and does not guarantee every skill improves or that all six skills are mastered. Recent reward, fixed-condition validation reward, per-goal experience, actual loss/entropy/KL and update/step counts come from the engine.

## Persistence and lifecycle

Current key: `mydesk.robotdog.ppo.v2`. Compatible rig-4/5 PPO actor/optimizer state migrates to rig 6; old evaluation screening is invalidated because mass/contact physics changed. Previous `mydesk.robotdog.v1` CEM data are removed when this page is opened on each device. No other app keys are removed. The changed observation size/control mechanism means CEM weights are not silently treated as compatible PPO weights. The new key stores the current actor/critic, three Adam states, RNG, update/step counts, integrated weights, goal/terrain settings, skill counts and up to 1,000 history points. An unfinished rollout buffer can be resampled after interruption; no full unfinished episode is promised to resume exactly. One public robotdog-only cloud checkpoint now shares actor, critic, Adam states and experience counters across devices.

Periodic checkpoints and pause/stop checkpoints save during use, not only at unload. Manual pause stops learning as well as observation. Hidden pages pause the worker between small work chunks; returning resumes only if the user had not paused. Reset asks confirmation and initializes only the new PPO key, retaining all other app data. A stale HTML form is refreshed via a versioned URL rather than clearing storage.

## Compact Fold layout

Page/stage titles, arm controls, foot contact lamps and decorative captions are removed. Contact state still exists internally for physics and PPO. The fourth telemetry value is actual PPO update count. The small shoe button is at the bottom-left of the scene; strength and robot/terrain camera focus selection are in details. Basic closed-panel layout is checked at 320×740, 360×740, 390×844, 768×1024, 960×600 and 1440×900 CSS pixels. Expanded help/skill sections use normal page scrolling. Device browser bars and accessibility font enlargement may change usable height.

## dog6: environment diversity, camera and shared learning

The chassis is narrower across the shoulders (0.22 m vs 0.30 m) while leg mount spacing and total mass remain unchanged. Hull collision width and inertia follow the new body width. Procedural grass is 3.5–13 cm, slightly darker than the terrain; stones and gravel use muted soil colours. Terrain focus holds the selected view target fixed; robot focus follows the base over the local ground. Orbit and zoom remain available by gestures; preset orientation and structure-view buttons are removed.

Optional randomization is off by default. When enabled, it can choose a terrain per episode, sample a friction coefficient (0–2) at a configured simulation-time interval, and apply either horizontal impulses (0–100 N·s) or sustained forces (0–1000 N, 0.05–20 s) at randomly selected body/leg locations. Waiting intervals are sampled after the previous load ends. The same seeded environment is reproducible. Loads enter generalized forces and COM acceleration; friction changes the solver's Coulomb impulse cap. No successful gait controller is injected. Fixed screening evaluations disable these randomizations, while training histories include the randomization settings in their context.

`robotdog-shared.mjs` uses the existing public client configuration with the separate `public.robotdog_shared_model` table, defined in `docs/sql/robotdog-public-checkpoint.sql`. The row is intentionally public read/write without sign-in, as requested. RLS and grants limit this table to select/insert/update of its single `main` row; no other app table is changed. A trigger stamps server revisions. PATCH compares the revision before writing; stale devices stop learning and apply the newer checkpoint instead of silently overwriting it. Independent Adam states from two devices are not mathematically merged. Only one learner should progress the shared checkpoint at a time.

At first connection an empty server is seeded from local PPO state. A never-connected device with existing trained state can replace a revision-1 empty initial checkpoint; later global resets cannot be undone by an old disconnected cache this way. Local working checkpoints and pending writes survive network interruptions; upload retries every 15 seconds and on training pause/stop. Idle clients check for newer revisions every 15 seconds. Opening an unchanged page does not write its old cache back. Reset requires confirmation and resets this shared robotdog checkpoint across devices. No account, password, subscription or new third-party SDK is introduced.

Checks: real PPO updates, gravity/contact, optional force/friction effects and deterministic replay, seeded two-device synchronization with optimizer restoration, stale-write rejection and offline retry, six responsive layouts and a larger graph on the Fold inner portrait viewport. RLS insert/update/revision behaviour was exercised under the anonymous role in a transaction rolled back afterwards; security advisors returned no findings. These checks do not establish long-horizon robot skill competence.
