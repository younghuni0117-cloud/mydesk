# Private career resume

`resume.html` is a public shell with no personal resume data. The `career-resume` navigation link is a child of the existing career folder. The protected article is `career-resume-main`; its title and placement are public, while public body/summary must remain empty under the existing blog privacy constraint. Actual content is stored in the existing non-exposed `mydesk_blog_private.post_content` table. No photos, identifying certificate/student/military numbers, personal content or actual passwords are committed to Git.

The page submits a password to the existing `blog_post_read` RPC over HTTPS, with `cache: no-store`, omitted cookies and a reader header. It never loads or uses a saved management session, never automatically unlocks, and never writes the body or password to local/session storage or the URL. Returned rich text is sanitized. The page has a restrictive CSP, no-referrer/noindex metadata and no external embedded image access. Visible content is cleared on explicit locking, page hiding/leaving, BFCache return and 10 minutes of inactivity. In-flight reads are aborted/invalidated when locked.

Initial access uses a server-side copy of the existing management bcrypt verifier; neither its hash nor its password is returned to the client or changed by installation. This creates an independent per-post password: subsequent management-password changes do not rotate it. The owner can edit the article and change its individual password using the existing blog editor. Existing authenticated management authorization retains its normal blog-editing powers. Keep the article private when editing.

Content is organized from user-provided material into source facts, common task descriptions, qualifications/training, expired-language-score status, matching criteria, writing drafts and explicit verification gaps. Draft sentences do not invent project outcomes, salary, seniority or tool experience. This is a prepared reference for later job matching/writing; there is no third-party AI API or automatic transmission of personal data.

Validation: real database anonymous/wrong-password denial, authorized-password reading and private-table denial using a rollback-only synthetic password (original verifier restored); empty public body/summary; synthetic browser checks for management-session independence, wrong/correct passwords, sanitization, no persistence, explicit/idle/visibility/reload locking and five screen sizes; navigation unit regression. Browser fixtures contain synthetic content only.

The blog renderer tolerates the shared shortcut header removing the old breadcrumb element, so the existing protected editor remains usable without changing the header layout.

## Structured resume manager

The resume page now provides a private in-page left category menu: basic profile, education, career, projects, papers, patents, certifications/training, languages, essays, job preferences and legacy material. Each category has add/edit/delete controls and field-specific forms. Existing HTML content remains untouched in the original protected post; the client groups its headings/subheadings into editable source records on first opening. It does not invent employer, qualification or performance fields from ambiguous text. Imported facts are marked as requiring source review. The first successful save persists the complete structured document. Original source remains available behind the same password.

`resume-model.mjs` defines the structured schema and pure CRUD/export functions. `sync/resume-items.sql` defines a non-exposed, RLS-enabled table and the fixed-profile `resume_profile` RPC. It reuses the existing resume post's password verification and lockout, checks the post is private, limits input, and enforces optimistic revision control. Read and write both require verification. Public wrappers are security-invoker; privileged code remains in the private schema with explicit authorization. No management token is loaded. Password, document and editor drafts stay in memory only; explicit/visibility/idle locking clears them. The private table is not directly available to anonymous or authenticated users. Published source contains no personal resume content, password, hashes or uploaded photos.

Server data is shared across devices; open the page with the existing resume password. Concurrent stale writes are rejected. Existing blog post editing is now only an original-source editor; the structured document is independently managed here, so subsequent blog edits do not silently overwrite saved structured records. Automatic job searching/AI essay writing is not implemented in this update; source and verification-status fields prepare grounded input for a later integration without transmitting personal data to another provider.

Validation: model CRUD, import classification/no invented facts, bounds and navigation unit tests; rollback-only database tests with a generated synthetic verifier checked no-password/wrong-password denial, authenticated load/save/restore, stale revision rejection, non-string rejection and direct table denial. Synthetic verifier and data were rolled back; the original remains private with empty public body/summary. Supabase security advisors returned no findings. New native-dialog UI and mobile interaction need actual browser/device verification; previous `scripts/verify-resume.cjs` targets the old RPC/UI and is not a verification of this version.
